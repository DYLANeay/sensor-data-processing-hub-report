\section{Mapping Between Views}
\label{sec:mapping}

The three views describe the same system from different sides, so they must
agree. Bass et al. stress that views are related~\cite{bass_software_2021};
Kruchten's 4+1 model makes the same point, with views kept consistent with
each other~\cite{kruchten_4plus1_1995}. The mapping is stored in the UML
model as relationships: each C\&C component carries a \texttt{trace}
dependency to its class, each assembly a \texttt{manifest} dependency to its
module, and each project reference a \texttt{reference} dependency to the
assembly it uses. \Cref{fig:view-mapping} draws all of it: each horizontal
band is one module, with its runtime components on the left, its classes in
the middle and its assembly on the right.

Classes with behavior become components, interfaces become connectors, and
the Core types become the data that travels on the connectors. One module
gives one assembly. The last row is the process itself: the entry assembly,
\texttt{SensorHub.Application.dll}, manifests the
\texttt{SensorHub} process of the C\&C view and loads the other five
assemblies. The only component that spans two modules is \texttt{startup}:
\texttt{Program} drives it and the classes of Configuration do the work,
which is why it belongs to both.

Because the mapping is stored in the model as relationships, we could check
it: one assembly per module (6/6), each component traces to at least one
class (10/10), each connector allowed by the uses view (10/10), the
\texttt{reference} dependencies equal to the \texttt{use} dependencies
(12 against 12), and each assembly nested in the .NET runtime (6/6). The
last two rules tie the C\&C and allocation views to the module view: no
component calls a component whose module it is not allowed to use, and the
build cannot contain a dependency the uses view forbids.

This is also what makes the modifiability scenarios measurable: adding a CSV
export sink, for example, is one class and one factory entry in the module
view, one component on the existing \texttt{IOutputSink} connector of
\texttt{hub} in the C\&C view, and three assemblies recompiled (Output,
Configuration, Application) in the allocation view.
