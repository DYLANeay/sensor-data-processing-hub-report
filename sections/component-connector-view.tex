\section{Component-and-Connector View}
\label{sec:cc-view}

The component-and-connector (C\&C) view shows what runs and how it
interacts. \Cref{fig:cc-view} shows the whole runtime structure, including
the startup phase that builds it.

\landscapefigure{uml/cnc-view/CnC.png}{Component-and-connector view of one running hub, with the
  configuration of \cref{lst:config}: two sources, four steps and two sinks.}{fig:cc-view}

\subsection{Style and components}

The overall style is call-return with a central mediator. The component
\texttt{hub} is the only one that calls the sources, the chain and the
sinks; they never call each other. Inside the chain, the steps form a
pipe-and-filter sequence in the sense of Garlan and
Shaw~\cite{garlan_shaw_1994}: the output of one step is the input of the
next, and no step knows its neighbors. The sequence is not realized by
pipes between the steps, though: \texttt{chain} calls each step in turn and
passes the result along. Unlike the MQTT broker of lab 3 of the
course~\cite{marsic_mqtt_nodate}, the components here call each other
directly: the hub is a single process in which everything is created and
wired at startup, and a source does not need to know who consumes its
readings, because it does not send them anywhere, it is asked for them.

The large \texttt{SensorHub} box in \cref{fig:cc-view} is the hub process;
the components inside it are its runtime parts, and the diagram says which
interface each of them provides. \texttt{startup} reads \texttt{config.json}
and creates and wires every component (this is the code of \texttt{Program}
together with the classes of Configuration). The \texttt{Console} is marked
external because it is the standard output of the process, not a part of it.

\subsection{Connectors and behavior}

The call connectors are assembly connectors named after the interface they
realize: the ball sits on the provider, the socket on the requirer.
\texttt{hub} pulls readings from the sources, passes each reading through
\texttt{chain}, and pushes the result to the sinks with one
\texttt{Write()} per reading and one \texttt{Close()} at the end;
\texttt{chain} calls its steps through ordered connectors
\texttt{ITransformation \{1\}} to \texttt{\{4\}}, in the order fixed by the
config file. The two alerters, \texttt{tempAlerter} and \texttt{co2Alerter},
are two instances of the same class, \texttt{ThresholdAlerter}: the CO$_2$
alert is one more entry in the config file, not new code. The data travelling on every call is a
\texttt{SensorReading}, which carries its alerts. The files are artifacts
outside the process: \texttt{config.json} and the CSV data are read,
\texttt{hub.log} is written.

After \texttt{startup} calls \texttt{Run()}, the loop reads the sources
round-robin: it takes one reading from each source in turn, passes it
through the chain, writes it to every sink, then waits \texttt{delayMs}
(200\,ms in \cref{lst:config}) so the dashboard visibly updates. A source
that is exhausted leaves the rotation. When every source is exhausted,
\texttt{hub} closes the sinks and \texttt{Run()} returns. Everything runs in one thread, the main thread, so
the state kept by \texttt{smoother} and \texttt{dashboard} needs no locking.
The configuration file sets, without any code change, which sources, steps
and sinks exist and with which parameters; the multiplicities live in the
module view.

\subsection{Design and modeling decisions}

The tactics behind the view are those of \cref{sec:module-view}; here we
discuss what the diagram adds and how to draw it.

The order of the configuration, convert then smooth then alert, is
a configuration choice: the thresholds are written in the converted unit,
and alerting on smoothed values avoids alerts caused by one noisy reading.
Another order only needs a change in the config file.

\begin{itemize}
  \item We considered nesting the steps inside \texttt{chain}, but nesting
  reads as composition, while the module view says aggregation: a step can
  exist without a chain, and the two views would contradict each other. The
  steps are therefore drawn next to \texttt{chain}.
  \item We drew ordered connectors from \texttt{chain} to each step instead
  of data-flow arrows from step to step: the steps never call each other,
  so flow arrows would show an interaction that does not exist.
  \item \texttt{startup} is linked to \texttt{hub} by two connectors,
  \texttt{create} and the \texttt{Run()} call, because creation happens
  once while the call is the runtime entry point. The startup phase stays
  in the diagram, because creating the components from the config file is
  one of the main decisions of this architecture.
\end{itemize}

The single thread is a deliberate simplicity choice: the behavior is
deterministic and easy to test and demo. It has a known cost: a source that
blocks (a future socket feed waiting for data, for example) would stop the
whole hub. The alternative, one task per source filling a queue that
\texttt{hub} consumes (the producer/consumer variant of the \emph{introduce
concurrency} tactic), would not change the interfaces, only add a private
queue to \texttt{hub}; we keep it as a modifiability scenario rather than
build it now.
