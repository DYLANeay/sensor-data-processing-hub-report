\section{Modifiability Scenarios}
\label{sec:modifiability}

Each scenario follows the quality-attribute scenario form of
Bass et~al.~\cite{bass_software_2021}: source, stimulus, artifact,
environment, response and response measure. Modifiability is treated in the
corresponding course lecture~\cite{wiklund_ch8_nodate}. We chose four changes
that are likely to come, and the response measures are read off the module
and allocation views (\cref{tab:allocation-changes}).

\subsection{Change a unit conversion}
\label{sec:scenario-conversion}

The assignment already names Celsius to Fahrenheit, and the unit a user
wants depends on who reads the dashboard, so conversions will change.
\texttt{UnitConverter} applies a linear formula (value $\times$ factor $+$
offset) whose parameters come from \texttt{config.json}, so this change
needs no code.

\begin{itemize}
  \item \textbf{Source:} the person who deploys the hub.
  \item \textbf{Stimulus:} wants temperatures shown in kelvin instead of
  degrees Fahrenheit.
  \item \textbf{Artifact:} the \texttt{converter} entry of the transformation
  chain in \texttt{config.json}.
  \item \textbf{Environment:} deployment time, hub stopped.
  \item \textbf{Response:} sets the target unit to \texttt{K}, the factor to
  1 and the offset to 273.15, and restarts the hub.
  \item \textbf{Response measure:} 1 file edited (\texttt{config.json}),
  0 source files changed, 0 assemblies recompiled, done in under 10 minutes.
\end{itemize}

\subsection{Add a socket feed source}
\label{sec:scenario-socket}

The assignment names a socket feed as a third kind of sensor, and real
sensors push their readings over the network, so this is the next source we
expect.

\begin{itemize}
  \item \textbf{Source:} a developer.
  \item \textbf{Stimulus:} wants to ingest readings from a TCP socket in
  addition to the CSV file and the random generator.
  \item \textbf{Artifact:} the Ingestion module, \texttt{SourceFactory},
  \texttt{config.json} and \texttt{Hub}.
  \item \textbf{Environment:} development time.
  \item \textbf{Response:} adds one class \texttt{SocketSensorSource}
  implementing \texttt{ISensorSource}, one entry in \texttt{SourceFactory}
  and one source entry in \texttt{config.json}. A socket blocks while it
  waits for data, so \texttt{Hub} gets the producer/consumer queue described
  in \cref{sec:cc-view} (one task per source); the change is private to
  \texttt{Hub} and no interface changes.
  \item \textbf{Response measure:} 1 new class, 1 factory entry, 1 config
  entry and a private change in \texttt{Hub}; 0 lines changed in Processing,
  Output and Core; 3 assemblies recompiled (Ingestion, Configuration,
  Application); the existing tests still pass; done within one working day.
\end{itemize}

\subsection{Add a CSV export sink}
\label{sec:scenario-sink}

The console dashboard and the log file are meant for watching the hub. The
next need is to keep the processed readings for later analysis, for example
as a CSV export.

\begin{itemize}
  \item \textbf{Source:} a developer.
  \item \textbf{Stimulus:} wants the processed readings and their alerts
  written to a CSV file, besides the console dashboard and the log file.
  \item \textbf{Artifact:} the Output module, \texttt{SinkFactory} and
  \texttt{config.json}.
  \item \textbf{Environment:} development time.
  \item \textbf{Response:} adds one class \texttt{CsvExportSink}
  implementing \texttt{IOutputSink}, one entry in \texttt{SinkFactory} and
  one sink entry in \texttt{config.json}; \texttt{Hub} writes to it through
  the existing \texttt{IOutputSink} connector.
  \item \textbf{Response measure:} 1 new class, 1 factory entry, 1 config
  entry; 0 lines changed in Ingestion, Processing, Core and the two existing
  sinks; 3 assemblies recompiled (Output, Configuration, Application); the
  existing tests still pass; done within 4 hours.
\end{itemize}

\subsection{Add a new sensor type}
\label{sec:scenario-sensor-type}

Environmental hubs usually grow new measurements, such as air pressure or
particulate matter. This is the expensive change of our architecture, because
the sensor type is an enumeration in Core.

\begin{itemize}
  \item \textbf{Source:} a developer.
  \item \textbf{Stimulus:} wants to process air pressure readings.
  \item \textbf{Artifact:} \texttt{SensorType} in Core and
  \texttt{config.json}.
  \item \textbf{Environment:} development time.
  \item \textbf{Response:} adds the value \texttt{Pressure} to
  \texttt{SensorType} and the thresholds for pressure in
  \texttt{config.json}. The CSV source parses the type by name, and the
  converter, smoother, alerter and dashboard take the sensor type as data, so
  none of them changes.
  \item \textbf{Response measure:} 1 line changed in Core plus config
  entries; 0 lines changed in the other modules; all six assemblies
  recompiled, since every project references Core
  (\cref{tab:allocation-changes}); done within 2 hours.
\end{itemize}
